# Implementation Plan

RAG chat web app over the PDF knowledge base in `knowledgebase/`. Each phase has success criteria to check off before moving on.

## Architecture

```
Browser (Next.js, :3000)
   |  POST /api/chat  (proxied by Next.js rewrites to the backend)
   v
FastAPI (:8000)
   |-- LangChain agent (create_agent) + InMemorySaver checkpointer (per-session chat memory)
   |      |-- tool: search_knowledgebase -> Chroma similarity search
   |      |-- LLM via OpenRouter (ChatOpenAI with OpenRouter base_url)
   |      |-- structured output: Pydantic AgentAnswer (API returns ChatAnswer)
   |-- Chroma vector store (local, built from knowledgebase/ PDFs)
          |-- OpenAI embeddings (text-embedding-3-small)
```

## Key Decisions

| Area | Choice | Reason |
|------|--------|--------|
| Chat memory | LangGraph `InMemorySaver` keyed by `session_id` (`thread_id`) | In-memory only, idiomatic for LangChain agents, lost on restart |
| Session id | Generated in the browser (`crypto.randomUUID()`), held in React state | No user management; "New chat" creates a new id |
| Vector store | Chroma persisted to `backend/chroma_db/` (gitignored) | Avoids re-embedding the 18 MB PDF on every start. This is a rebuildable cache, not application data |
| Ingestion | Runs automatically at startup if the collection is empty; also runnable manually | One less step for the user |
| PDF loading | `pypdf` `PdfReader` over every `*.pdf` found recursively in `knowledgebase/`, one document per page | Supports the nested folder structure; no need for `langchain-community` |
| Chunking | `RecursiveCharacterTextSplitter`, ~1000 chars, 150 overlap | Sensible default for technical prose and code |
| Retrieval | Top 5 chunks, returned with file path and page number | Allows source citations in the UI |
| LLM | OpenRouter model set by `CHAT_MODEL` env var, with a sensible default (e.g. `openai/gpt-5-mini`) | Easy to swap models |
| Response | Non-streaming JSON: `{answer, sources}` | Structured output keeps it simple; the UI shows a typing indicator while waiting |
| Structured output | `response_format=ToolStrategy(AgentAnswer)` | Works with any OpenRouter model that supports tool calling, not only those with native structured output |
| Search limit | System prompt tells the agent to search once, at most three times, then answer | Without it `gpt-5-mini` repeated near-identical searches and exceeded the 120 s proxy timeout |
| Sources | Built from the chunks the search tool actually returned in the turn, not generated by the model | Prevents hallucinated page citations |
| Frontend styling | Tailwind CSS + `@tailwindcss/typography`, `react-markdown` + `remark-gfm` + `rehype-highlight` for code blocks, IBM Plex Sans and Mono via `next/font` | The knowledge base is C#, so answers will contain code |
| Proxy timeout | `experimental.proxyTimeout: 120000` in `next.config.ts` | The default (~30 s) can cut off agent responses |
| Ports | Backend 8000, frontend 3000 | Defaults |

## API

`POST /api/chat`

```json
// request
{ "session_id": "uuid", "message": "What is a record type?" }
// response
{ "answer": "markdown text", "sources": [{ "file": "csharp_core.pdf", "page": 42 }] }
```

`GET /api/health` returns `{ "status": "ok" }`.

## Phase 2: Backend - Configuration and Ingestion

- `config.py`: `Settings` (pydantic-settings) reads `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `CHAT_MODEL`, paths for `knowledgebase/` and `chroma_db/`
- `ingest.py`:
  - `load_documents(path)` finds all PDFs recursively, loads pages with metadata (relative file path, page number)
  - `split_documents(docs)` chunks them
  - `build_vector_store()` embeds and stores chunks in Chroma; skipped if the collection already has data
  - `python -m app.ingest` rebuilds the store from scratch

  - [x] Store is populated, and a second run does not duplicate chunks

## Phase 3: Backend - RAG Agent and API

- `rag.py`:
  - Pydantic models: `AgentAnswer(answer)` (agent structured output), `Source(file, page)`, `ChatAnswer(answer, sources)` (API response), `ChatRequest(session_id, message)`
  - `search_knowledgebase` tool: returns the top 5 chunks formatted with file and page, with the retrieved documents as the tool artifact (`response_format="content_and_artifact"`)
  - Agent built with `create_agent(model, tools=[search_knowledgebase], system_prompt=..., response_format=ToolStrategy(AgentAnswer), checkpointer=InMemorySaver())`, where `AgentAnswer` holds only `answer`
  - System prompt: search with a focused query (once, at most three times), answer only from retrieved context, say so when the answer is not in the knowledge base, use Markdown
  - `ask(session_id, message) -> ChatAnswer`: runs the agent, then builds `sources` (deduplicated file and page) from the tool artifacts produced in the current turn
- `main.py`: FastAPI app with lifespan that builds the vector store if empty (on the first start, embedding the 18 MB PDF can take several minutes before the server accepts requests); `POST /api/chat`, `GET /api/health`

Success criteria:
- [x] Unit tests with fake embeddings and a small fake chat model that supports `bind_tools` and returns a scripted tool call, then the final answer (no network):
  - [x] Tool returns formatted chunks and the retrieved documents as its artifact
  - [x] `ask` returns a valid `ChatAnswer` whose sources come from the retrieved chunks
  - [x] Conversation memory: a second message in the same session sees the first; a different session does not
  - [x] `POST /api/chat` returns 200 with the response schema; invalid body returns 422
  - [x] `GET /api/health` returns ok
- [x] Manual check with the real model: a C# question returns a grounded answer with page citations, and a follow-up question ("give an example of that") uses the chat context

## Phase 4: Frontend - Chat UI

Design: a clean, centered single-column chat in the style of modern AI assistants.
- Header with the app name and a "New chat" button
- Empty state: centered title and short subtitle (no example questions, to keep it simple)
- Messages: user messages right-aligned in a subtle bubble; assistant answers rendered as Markdown with syntax-highlighted code blocks, and source chips (file, page) underneath
- Animated typing indicator while waiting; auto-scroll to the latest message
- Input: auto-growing textarea pinned to the bottom; Enter sends, Shift+Enter adds a new line; disabled while a request is in flight
- Inline error message if the request fails
- Light and dark mode following the system preference; responsive down to mobile width
- Typography with IBM Plex Sans and IBM Plex Mono (via `next/font`)

## Phase 5: Start and Stop Scripts

- `start-backend` / `start-frontend` (`.ps1` and `.sh`): `start-backend` runs `uv sync` and starts `uvicorn`; `start-frontend` runs `npm install`, builds and runs `next start`. Each exits early if its server is already running; otherwise it starts the server in the background, logs to `*.log`, waits until the server responds (first-start ingestion can take minutes), and only then writes its PID to `scripts/*.pid`, so a failed start never replaces a good PID file
- `stop-backend` / `stop-frontend`: stop that server's process tree using its PID file and remove the file

Success criteria:
- [x] On Windows, `start-backend.ps1` then `start-frontend.ps1` bring up both servers; `http://localhost:3000` loads and `/api/health` is ok through the proxy
- [x] `stop-frontend.ps1` and `stop-backend.ps1` each stop only their own server
- [x] Running a start script while its server is already running reports it and leaves the running server and PID file untouched
- [ ] The `.sh` scripts are written to the same behaviour (syntax-checked only: `setsid` is not available in Git Bash)
